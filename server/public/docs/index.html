Integration Guide

Put a polished mini game inside your website or mobile app. Your system logs your users in and sells the coins; we run the game. About 10 minutes for the first version.

Quick start

  1. Create an account and copy your API key.
    Sign up at {{HOST}}. Your API key (mgs_…) is shown once right after sign-up and whenever you press Rotate under API key & webhooks. It is one key for your whole account, whichever games you own.
  2. Buy a game and note its game ID.
    Each game you own has a game ID (lic_…), shown in the dashboard and in GET /api/v1/games.
  3. Add one endpoint to your backend.
    After your own login has identified the user, it calls POST {{HOST}}/api/v1/sessions with the API key, the game ID and your id for that user, and returns the playUrl to your front-end. See the examples (Node.js, Python, Java, PHP, cURL).
  4. Show the game.
    Open that playUrl in an iframe (website) or a WebView (Flutter, Android, iOS), or use the 3-line JavaScript SDK. The player lands straight in the game: no sign-in screen, because you already know who they are.
  5. Connect the coins (when you are ready).
    Switch the game to managed wallet in Settings, then call credit when you sell coins and debit for a cash-out. See Coins. Optionally receive results with webhooks.
Try it before you code: dashboard → your game → Customize. The preview on the right is the real game.

How it works

The split of responsibilities is deliberately simple, and the same for every client:

Your systemOur system
Your users, their passwords, login, security, KYCThe game: rules, odds, fairness, the shared round clock
Deciding who may playShort-lived play sessions (15 minutes)
Selling coins, refunds, cash-outsThe coin ledger (when you use the managed wallet)
Your own database and screensPlayers' history, results and the dashboard for you
  • API key (mgs_…): the secret that proves a request comes from your server. One per account. Server only.
  • Game ID (lic_…): which of your games to use. Not secret. The same key serves all your games.
  • Player id: your id for a person (a user id, an email hash, anything stable). We never see passwords and never check logins.
  • Play link (playUrl): created by your server for one player, expires after 15 minutes, safe to hand to a browser or app.
  • Customization: images, video, sounds, texts, rules and odds are set in the dashboard and apply to every session of that game.

Players and identity

Your server tells us who is playing when it creates the session. Because the request is authenticated with your secret API key, we trust the player id you send: nobody can play as someone else, since a player never talks to us before your server vouches for them.

FieldRequiredDescription
playerIdyes*Your id for this person: 1-64 characters, letters, digits and _ . : @ -. Always the same id for the same person. We treat it as an opaque string.
displayNamenoShown in rankings and winner lists (1-40 characters). Updated every time you send a new one.
avatarUrlnoAn https picture address (kept for rankings).

* Required unless the game has guest login switched on.

  • A player belongs to one game: the same person in two of your games has two balances and two histories.
  • The player exists as soon as you create the session (or credit coins), so you can credit coins before the first time they open the game.
  • Guest login (game → Settings, off by default) lets players type their own name. It is meant for demos. With it off, the game never shows a name screen and the typed-name endpoint is closed.
Never send a password or a secret as playerId. Use an id that is safe to appear in your own logs.

Coins (wallet)

Each game has a wallet mode (game → Settings):

ModeWhere coins come fromUse it for
Demo wallet (default)New players start with the starting balance from Customize and can take a free refill when they run out.Demos, trying the game, free-to-play
Managed by my serverNew players start with 0. Your server adds coins with credit and removes them with debit. The free refill is off.Real coin economies you control

Typical flows

  • A player buys coins in your app: after your payment succeeds, call credit with a reference that is unique per order (for example order-1001). The game shows the new balance within a second or two, even while it is open.
  • A player cashes out: call debit. If they have less, you get 402 insufficient_balance and nothing moves.
  • A player runs out of coins in the game: the game shows a message and sends the needCoins event to your page or app, so you can open your own shop.
  • You want to reconcile: read GET …/transactions. Every coin movement is listed, including the bets and wins the game made.

Safe retries: reference

Networks fail. Every credit and debit needs a reference that is unique per operation. If you send the same operation again with the same reference, you get the same answer ("duplicate": true) and coins never move twice. If you reuse a reference for a different amount, player or direction you get 409 reference_conflict.

So your rule is simple: retry until you get an answer. A timeout, a 5xx or a dropped connection are all safe to retry with the same reference.
If your players' coins are real money, your licensing, auditing and responsible-gaming duties apply to you. We provide the game and the ledger; compliance stays with you.

Webhooks

We can call your server when something happens, so you do not have to poll. Set the address and copy the signing secret under API key & webhooks (one address per account). Press Send test to see a delivery arrive.

What we send

POST to your address, Content-Type: application/json, body:

webhook.testYou pressed Send test.

Verify the signature

Headers on every request:

HeaderValue
X-Minigame-EventThe event type
X-Minigame-DeliveryThe event id (same as id in the body)
X-Minigame-TimestampUnix seconds when we sent it
X-Minigame-Signaturev1= + hex HMAC-SHA256 of "<timestamp>.<raw body>" using your signing secret
  1. Take the raw request body (before any JSON parsing).
  2. Compute HMAC-SHA256(secret, timestamp + "." + rawBody) as lowercase hex and prepend v1=.
  3. Compare it to X-Minigame-Signature with a constant-time comparison.
  4. Reject the request if the timestamp is more than 5 minutes old (protects against replays).
  5. Answer with any 2xx status. Do the heavy work afterwards.

Retries

Any answer that is not 2xx, or no answer within 8 seconds, counts as a failure. We retry after 10 s, 1 min, 5 min, 30 min, 2 h and 6 h (seven attempts in total), then give up. Every attempt is visible under API key & webhooks → Recent deliveries, where you can also press Retry now. Because a delivery can arrive more than once, treat id as an idempotency key.

The address must be https and must not point to a private or local network. Redirects are not followed.

Every error has the same shape: { "error": "human readable message", "code": "machine_code" }. Program against code.

StatuscodeMeaning and fix

400player_id_requiredSend playerId, or allow guest login for the game.
400invalid_player_id, invalid_displayName, invalid_avatarUrlCheck the allowed characters and lengths.
400invalid_amount, reference_required, invalid_noteAmount must be a whole number; every money call needs a reference.

404game_not_found, player_not_foundThe game ID belongs to another account, or the player was never seen.
409wallet_not_enabledSwitch the game to managed wallet in Settings.
409reference_conflictThat reference was already used for a different operation. Use a new one.
429rate_limitedSlow down. Limits: 300 sessions and 600 wallet calls per minute.

Server examples

Replace GAME_ID with your game ID. Keep the API key in an environment variable named MINIGAME_API_KEY. Your front-end calls your /game-session endpoint, never ours.

Create the session

Add coins after a sale

Many games, one key. Just send a different game ID. You never manage more than one secret.
Create a new session each time a player opens the game. Do not cache or reuse a playUrl for more than a few minutes.

Show the game

Your front-end asks your endpoint for the play link and shows it.

The games are built for portrait screens (like a phone) and scale to fit any box: they fill the height and use your theme background for the rest. Recommended size: 480 x 760 or the full screen of a phone.

Android needs <uses-permission android:name="android.permission.INTERNET"/>. iOS needs nothing extra for https links. In React Native use react-native-webview and read events from onMessage.

Events from the game

Every event is { source: "minigames", type, data }. Websites get them through the SDK's onEvent (or window.addEventListener('message')), Flutter through the MiniGames JavaScript channel.

typedataWhen
login{ username, balance }The player is in the game (username is the display name)
ready{ game }The game is on screen
round{ game, round, bet, win, hits, balance }A round was paid. hits lists the winning option codes.
needCoins{ balance }Managed wallet only: the player tried to bet with too few coins. Open your own shop.
exit{}The player pressed the back button. Close the game or navigate away.
error{ message }Web SDK only: your session endpoint failed

Events are for your UI (analytics, opening a shop). The authoritative record is on our server: use the webhooks or the transactions API for anything that matters.

Players & results

Open My games → your game → Players & results to see, live: total players, rounds, wagered and paid out, payout rate; rounds per day and top winners; every player with their id, balance, rounds, wagered, won and last seen (searchable, sortable); a live feed of results filterable per player; every coin movement of a player (Coins button); and CSV export. Players you test with from the Customize preview are not counted.

Integration checklist

Before you go live:

  • The API key is only on your server (an environment variable), never in website code, an app or a repository.
  • Your /game-session endpoint checks that the caller is logged in to your system before it asks us for a session.
  • You send a stable playerId (the same id every time for the same person).
  • Guest login is off for the live game; wallet mode matches your economy.
  • Every credit and debit has a unique reference (for example your order id) and is retried on timeouts.
  • You handle 402 insufficient_balance and 409 reference_conflict explicitly.
  • Your webhook endpoint verifies the signature on the raw body, checks the timestamp, answers 2xx quickly and ignores repeated ids.
  • You use Send test and see delivered in the delivery log.
  • You listen for the needCoins event and open your shop.
  • "Allowed websites" lists your sites (optional hardening).
  • You know how to rotate the key (dashboard → API key & webhooks).

Security

  • Keep the API key in an environment variable on your server. Never in website JavaScript, a mobile app, a public repository or a screenshot.
  • Lost or leaked? Dashboard → API key & webhooks → Rotate key. The old key stops working immediately for all your games, and the new one works for all of them.
  • We never see your users' passwords. The player id you send is the identity: only send ids for users your system has authenticated.
  • Webhooks are signed with a secret only you and we know; verify them and reject old timestamps.
  • Optionally list your websites under game → Settings → Allowed websites. Browsers then refuse to show the game anywhere else (mobile WebViews are not affected).
  • Results are decided on our server with a cryptographically secure random generator. Players cannot change a result, and the odds are never sent to the game.
  • Play links expire after 15 minutes. Treat each one as belonging to one player.
If your front-end ever contains mgs_, rotate the key now.

FAQ

Do my players need an account with us? No. They never see us: your server vouches for them with your own id.

Is the in-game currency real money? It is whatever you decide: you sell coins in your own system and credit them. We only keep the balance and the history.

Can two people share a player id? Not inside the same game: the id is the person. The same id in another game is a separate player.

A player ran out of coins. Demo wallet: the game offers a free refill. Managed wallet: the game sends needCoins so you can sell them more.
